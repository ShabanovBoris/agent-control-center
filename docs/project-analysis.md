## Архитектура и путь сообщения

Панель — React-интерфейс для управления сессиями на нескольких Agent Host Protocol (AHP) хостах. В разработке Vite обслуживает UI на loopback и проксирует `/ws`; в production браузер открывает WebSocket `/ws` к backend. Браузер не подключается к AHP-хостам напрямую.

1. Компоненты React подписываются на состояние каналов через [`src/store.ts`](../src/store.ts). Команда интерфейса отправляется как `{t: "call", id, call}`; просмотр канала — как `watch`.
2. [`server/index.ts`](../server/index.ts) принимает только `/ws`, проверяет upgrade и разбирает сообщения панели. Он передаёт команды в [`server/hub.ts`](../server/hub.ts), который через AHP SDK (`MultiHostClient`) вызывает методы хоста или отправляет ему actions.
3. AHP-хост — источник актуального состояния сессий и чатов. Он выполняет работу агента и публикует снимки каналов и actions. Hub поддерживает в памяти [`ChannelMirror`](../server/mirror.ts): снимок плюс применённые actions с `serverSeq`. Это кэш для синхронизации, а не авторитетное хранилище.
4. [`shared/protocol.ts`](../shared/protocol.ts) задаёт контракт браузер ↔ backend, а [`shared/reduce.ts`](../shared/reduce.ts) использует редьюсеры AHP. Hub передаёт снимки подписчикам и рассылает применённые actions; `src/store.ts` обновляет своё состояние, после чего React перерисовывает UI.

Состояния backend-зеркала и браузерного Store находятся в памяти процессов. Файл client ID в `FileClientIdStore` нужен SDK для replay событий после перезапуска backend; это не копия истории сессий. Физическое устройство хранилища конкретного хоста здесь не проверялось.

При потере связи браузер сохраняет список подписок, отклоняет ожидающие RPC и повторяет соединение через 1,5 секунды. После открытия он заново отправляет `watch` для каждого канала и получает свежие снимки; незавершённые команды автоматически не повторяются. Backend отпускает подписки закрывшегося браузера. При переподключении AHP-хоста Hub использует replay SDK и повторно загружает снимки отслеживаемых каналов. [`ChannelMirror`](../server/mirror.ts) упорядочивает их по `serverSeq`, чтобы старый снимок или action не откатил новое состояние.

### Доступ и `debug-ui`

- Основная конфигурация [`hosts.json`](../hosts.json) привязывает backend к `127.0.0.1`. Для `/ws` [`server/index.ts`](../server/index.ts) требует совпадения `Origin` и `Host` и loopback-имени; комментарий к проверке отмечает защиту от чужих сайтов и DNS rebinding. Токены AHP backend читает из `tokenFile` при подключении в [`server/config.ts`](../server/config.ts); в протокол UI токен не включается.
- Конфиг `listen` принимает любое строковое имя хоста, а привязка выполняется по нему напрямую. Поэтому loopback сейчас — настроенное и документированное ограничение, но не инвариант валидации. При bind на сетевой интерфейс проверки `Origin`/`Host` не являются аутентификацией для произвольного сетевого клиента, который может сформировать эти заголовки. См. приоритетный вывод ниже.
- Доступ с телефона реализован отдельным listener на `127.0.0.1:8092`. Его HTTP-маршруты отдают только собранные статические файлы и проверяют заголовки Tailscale Serve — настроенные `Host`, HTTPS и `tailscale-user-login`. Однако тот же listener принимает `/ws` через общий `acceptBrowserConnections` и `onBrowser` в [`server/index.ts`](../server/index.ts): WebSocket проходит те же проверки Tailscale и дополнительно требует точный настроенный `Origin`, затем получает обзор и состояние подписанных каналов и может вызывать команды Hub, в том числе `readResource` и `sendMessage`. Поэтому авторизованный пользователь Tailscale получает данные и возможности панели, включая ресурсы, которые предоставляет AHP-хост; это API-доступ, а не раздача содержимого через статические HTTP-маршруты. См. [`server/phone-access.ts`](../server/phone-access.ts) и [`server/index.ts`](../server/index.ts).
- `debug-ui` — отдельная минимальная резервная/диагностическая панель, а не часть React-приложения или Hub. Node-сервер на `127.0.0.1:5174` обслуживает статические файлы и HTTP API; собственный клиент из [`debug-ui/ahp.mjs`](../debug-ui/ahp.mjs) обращается прямо к AHP-хостам, показывает сессии и последние ходы и поддерживает базовые команды. Он отдельно читает `tokenFile` на сервере и проверяет локальный `Host`/`Origin` в [`debug-ui/server.mjs`](../debug-ui/server.mjs).

## Подтверждённые расхождения и риски

### P1 — клиентская проверка типов сломана на результате инструмента

**Источник.** В [`src/ui/ToolResultsDisplay.tsx`](../src/ui/ToolResultsDisplay.tsx#L23) и `:33` используются `ToolResultContentType.Image` и `.File`, а также поля `mimeType`, `data`, `name`. Установленный и закреплённый в [`package-lock.json`](../package-lock.json) SDK — `@microsoft/agent-host-protocol@1.1.0`; проверенные типы `ToolResultContentType` содержат `Text`, `EmbeddedResource`, `Resource`, `FileEdit`, `Terminal`, `Subagent`, но не `Image` или `File`. В частности, встроенные бинарные данные описаны как `EmbeddedResource` с `contentType` и `data`.

**Влияние.** `npm run typecheck` завершается с TS2339 на отсутствующих enum-элементах и полях. Текущая ветка компонента также не соответствует discriminated union SDK. Production-сборка Vite проходит, но сама по себе проверку типов не выполняет. README дополнительно обещает рендер текста, изображений и файлов в [`README.md`](../README.md#L242), что не подтверждается работающим типизированным кодом.

**Следующий шаг.** Отдельная задача AGENTHOS-4: согласовать отображение с типами и вариантами AHP 1.1.0, определить обработку встроенных ресурсов и resource-ссылок и добавить проверки рендеринга. В рамках этого анализа код и зависимости не менялись.

### P1 при сетевой привязке — loopback не закреплён в конфигурации

**Источник.** [`server/config.ts`](../server/config.ts#L27) проверяет, что `listen.host` — строка, но не ограничивает её loopback-адресами; [`server/index.ts`](../server/index.ts#L207) слушает именно указанный адрес. Проверка WebSocket на `Origin` и `Host` в `:84` не устанавливает личность клиента. При этом [`README.md`](../README.md#L173) предписывает оставлять backend на loopback, поскольку он выполняет команды агентов от имени пользователя.

**Влияние.** При штатном `127.0.0.1` backend не опубликован в локальной сети. Если конфигурацию изменить на публичный интерфейс, сетевой клиент, способный подделать заголовки HTTP, сможет пройти проверку upgrade и отправлять команды; отдельной аутентификации для основного `/ws` нет.

**Следующий шаг.** Отдельная задача AGENTHOS-5: либо отклонять небезопасный `listen.host` при загрузке конфигурации, либо спроектировать явную аутентификацию для осознанного удалённого доступа. Сейчас удалённый сценарий для телефона оформлен отдельно через Tailscale Serve.

### P2 — документация отрицает показ изменений файлов

**Источник.** [`README.md`](../README.md#L224) включает просмотр изменений файлов в список отсутствующих возможностей. Но [`src/SessionView.tsx`](../src/SessionView.tsx#L368) собирает `FileEdit` из результатов инструментов и подключает `FileEditDisplay` (`:387–388`); [`src/ui/FileEditDisplay.tsx`](../src/ui/FileEditDisplay.tsx#L41) показывает список и построчный diff, в том числе для загружаемого changeset. Memory Bank повторяет ограничение как отсутствие отдельных представлений файловых изменений в [`memory-bank/progress.md`](../memory-bank/progress.md#L8).

**Влияние.** README неверно описывает доступную возможность. Реализация ограничена изменениями, опубликованными хостом для конкретного хода; это не общий файловый браузер и не просмотр произвольных изменений на диске. Отсутствие отдельного представления терминала остаётся отдельным ограничением.

**Следующий шаг.** Задача AGENTHOS-6 уточняет README и Memory Bank: описывает per-turn просмотр `FileEdit`/changeset и сохраняет отдельно реальные ограничения по терминалам и общему просмотру файлов. Memory Bank в этой задаче не изменялся.

**Следующий шаг.** Актуализация Memory Bank с датированными результатами и удаление устаревшего указания о Git включены в AGENTHOS-6. Запрошенный scope ограничивался этим отчётом, поэтому записи оставлены без изменений.
