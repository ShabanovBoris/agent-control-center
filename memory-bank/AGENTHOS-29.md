# AGENTHOS-29: переименование агентных сессий и терминалов

Статус: сделано и слито — PR [#23](https://github.com/ShabanovBoris/agent-control-center/pull/23),
squash `785a3e2`. Живая проверка на стенде: 10/10 сценариев (см. «Проверки»).

## Решение владельца (принято до реализации)

- **Автозаголовок терминала = строка первой отправленной непустой команды целиком**, с лимитом
  длины и маскировкой известных форматов секретов. Остаточный риск принят владельцем: та же
  строка уже видна в scrollback того же PTY на том же устройстве, заголовок не расширяет
  поверхность. Альтернатива «только имя программы из первой команды» отклонена — критерий
  приёмки требует именно первую команду.
- **Подписи хранятся в `localStorage` этого браузера** (как уже было на `#terminal`): на хост,
  в другие браузеры и на другие устройства не уходят.
- **Гарантия только по данным AHP**: если хост не присылает `terminal/commandExecuted`, строка
  остаётся с именем папки. Починка хоста в задачу не входит.

## Найдено на живом стенде: кириллица в PTY (вне границ задачи)

Проба подтвердила документированное в AGENTHOS-26 ограничение и уточнила его природу. Симптом
хуже, чем «искажение `commandLine`»: **команда с кириллицей не исполняется вовсе**, а её текст
попадает мусором в следующую команду.

Что происходит на local-хосте (`bash`/`zsh` в PTY панели):

1. `locale` внутри PTY показывает `LC_CTYPE="C"`: у процесса хоста нет `LANG`/`LC_ALL`/`LC_CTYPE`.
2. Панель отправляет корректный UTF-8 (`terminalInput` по одному символу, кадры `п`,`р`,`и`… —
   проверено перехватом WS-кадров), так что дело не в xterm и не в `terminalInput`.
3. Shell в C-локали не считает байты UTF-8 символами: readline рисует их octal-escape'ами
   (`\320\277…`), портит буфер строки и теряет `\r` — команда не запускается.
4. Следующая ASCII-команда приходит хосту с приклеенным мусором: `commandLine` =
   `"echo ascii-afterecho ascii-twoecho ÿffffffffffffd0…"`. Отсюда же мусор в автоимени.

Воспроизведено **без панели**: `pty.fork()` + `/bin/bash --norc -i` с пустыми `LANG`/`LC_ALL`/
`LC_CTYPE` даёт тот же octal-эффект; с `LANG=en_US.UTF-8` кириллица работает штатно. Значит
корень — окружение PTY у хоста, а не наш код.

Вероятное место починки (follow-up, не эта задача): в лаунчерах хостов рядом с
`server/terminal-env.ts` выставлять UTF-8 локаль (`LANG`/`LC_ALL` + `LC_CTYPE`), как уже
делается для `TERM`/`COLORTERM`. Ограничение: `en_US.UTF-8` есть не на любом Linux-хосте —
нужен выбор доступной локали. Отдельно проверить, не влияет ли это на вывод TUI-агентов
(AGENTHOS-28).

До починки хоста README и этот файл фиксируют фактическое поведение: команда с кириллицей не
исполняется, `commandLine` приходит искажённым и приклеенным к следующей команде, панель это не
«чинит». Follow-up — AGENTHOS-30 «UTF-8 локаль в PTY терминалов».

## Граница и остаточные риски

- Живой UI проверен на local-хосте; wbllm/glm не проверялись отдельно (тот же код панели,
  различие — только лаунчер хоста).
- Хост без command detection оставляет имя по умолчанию — согласовано с владельцем.
- Маскировка секретов в автоимени best-effort: неизвестный формат может остаться в `localStorage`.
- Имя по первой команде — только по живому `terminal/commandExecuted`; обрезанный снимок канала
  не даёт восстановить пропущенную первую команду.
- Кириллица в PTY — дефект хоста, вынесен в follow-up (см. выше).
