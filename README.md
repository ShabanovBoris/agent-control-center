# Agent Control Center

Панель для управления сессиями Claude и Codex на нескольких AHP-хостах (Agent Host Protocol).
Панель не запускает агентов сама: она подключается к хостам, которые ими управляют, поэтому те же
сессии остаются доступны из VS Code.

## Запуск

Нужны Node 22+ и VS Code с подкомандой `code agent host`.

```bash
npm install
```

Одна команда из корня проекта поднимает dev-стенд целиком:

```bash
npm run up
```

Она запускает локальные хосты (`local` на 8089, `wbllm` на 8093, `glm` на 8094), backend на 8090
(и phone listener на 8092, если настроен `.local/phone-access.json`) и Vite на 5173.
Готовность объявляется по наблюдаемому состоянию: хосты найдены в реестре VS Code, backend
прислал `overview` с `connected` для всех локальных хостов, Vite отдал `200` на `/`. Затем в терминале видны
адреса; `Ctrl+C`, `SIGTERM` и `SIGHUP` гасят всё, включая `code-tunnel` и `code-server`.

Повторный `npm run up` при полностью живом стенде ничего не запускает и возвращает `0`.
Если стенд поднят частично или порт занят чужим процессом, команда перечисляет состояния,
ничего не запускает и возвращает `1`: `up` управляет только своими процессами.

Перед запуском проверяются:

- `.local/model-provider.env` с `WBLLM_API_KEY` и `GLM_API_KEY` (шаблон — `model-provider.env.example`);
- VS Code Stable по стандартному пути; `VSCODE_CLI` принимается, только если указывает на его
  `code-tunnel` или `bin/code` — иначе панель не найдёт запущенный хост, и `up` предложит
  ручной `npm run host`;
- свободные порты 8089, 8093, 8094, 8090, 5173 (и 8092, если включён доступ с телефона).

`ACC_PORT` с другим портом и `ACC_MOCK_HOST_URL` для `npm run up` отклоняются: стенд должен
слушать `listen.port` из `hosts.json`. Журналы хостов остаются в `.local/host.log` и
`.local/wbllm-host.log` и `.local/glm-host.log`; вывод backend и Vite идёт в терминал с префиксами `[backend]`/`[web]`.
Первый запуск может скачать серверную сборку VS Code (~600 МБ); `up` ждёт до 10 минут и печатает
прогресс.

`--prod` не поддерживается: production-панель и телефон — это `npm run build` и `npm run server`
(phone listener отдаёт `dist` на 8092 через Tailscale).

### Автозапуск при логине (macOS)

LaunchAgent ставится одной командой и живёт вне Git:

```bash
npm run autostart:install                  # автозапуск без удержания сна
npm run autostart:install -- --keep-awake  # плюс caffeinate на время работы up
npm run autostart:status
npm run autostart:uninstall
```

Команда создаёт `~/Library/LaunchAgents/com.agentcontrolcenter.up.plist` и запускает тот же
entrypoint, что `npm run up`, но напрямую (`node --import tsx scripts/up.ts --supervised`):
npm не пробрасывает сигналы дочернему процессу надёжно, а launchd должен сигналить `up`.
`WorkingDirectory` — корень проекта, `PATH` содержит каталог текущего `node`, поэтому
`start-host.sh` находит `node` и `openssl`. Секретов в plist нет: провайдер читается хостом
из `.local/model-provider.env` относительно корня проекта. launchd **не наследует** окружение
интерактивного shell: `ACC_CONFIG`, `AHP_PROVIDER_ENV_FILE`, `VSCODE_CLI`, `AHP_USE_BUNDLED_SDK`
и другие переменные из терминала не попадут в job. Стандартные пути (`hosts.json`,
`.local/model-provider.env`) работают; нестандартные нужно задавать через `WorkingDirectory`
или переписать plist осознанно. `autostart:install`, `status` и `uninstall` по той же причине
всегда читают `hosts.json` и `.local` (а не `ACC_CONFIG`/`ACC_STATE_DIR`) и предупреждают,
если эти переменные заданы в shell: диагностика должна смотреть туда же, куда job.

Параметры job: `RunAtLoad=true`, `KeepAlive={SuccessfulExit:false}`, `ThrottleInterval=30`.
`up` возвращает `0` только при осознанной остановке (Ctrl+C, `bootout`, выход из системы)
или когда стенд уже под управлением; падение даёт `1`, и launchd повторяет запуск не чаще
раза в 30 секунд. `StandardOutPath`/`StandardErrorPath` — `.local/up.log` (режим `0600`,
без ротации; очистить можно через `: > .local/up.log`). В `--supervised` строки `up` и его
дочерних процессов получают ISO-время.

`autostart:install` идемпотентен: работающий job с тем же plist не трогается; загруженный,
но остановленный job поднимается `launchctl kickstart` **без** `-k` (активные ходы не
прерываются); незагруженный — `bootstrap`. Изменённый plist (например, другой путь `node`
после обновления через nvm) при работающем job не применяется: установка просит `--force`,
потому что перезапись plist выгружает job и перезапускает `up`, прерывая активные ходы.
С `--force` (или если job не запущен) новый plist проверяется `plutil -lint`, job
выгружается (`bootout`), и только после исчезновения job файл заменяется. Отказ из-за
изменённого plist возвращает `1` и ничего не меняет. Чужой plist без маркера тоже требует
`--force`.

`autostart:uninstall` выгружает job, ждёт исчезновения job и завершения запомненного pid `up`,
удаляет plist и только после этого ждёт освобождения портов 8089, 8093, 8094, 8090, 5173 (и 8092,
если настроен телефон). Если job не выгрузился, команда возвращает `1` и **не удаляет plist**,
чтобы состояние оставалось обратимым. `.local/up.log`, `up-state.json` и журналы хостов
не удаляются — их можно убрать вручную.

Keep-awake включается только флагом: `caffeinate -i -m -s -w <pid up>` держит систему
и диск awake, но не мешает гаснуть дисплею; `-w` завершает `caffeinate` вместе с `up`,
даже если супервизор убит. Глобальные настройки энергии (`pmset`) не меняются.
Закрытая крышка Mac всё равно усыпит систему.

Восстановление в режиме launchd:

- ошибки **до** готовности остаются fail-fast: выход любого child сразу прерывает ожидание,
  остальные процессы гасятся, код `1`, launchd повторяет запуск; долгого ожидания таймаута нет;
- владение backend/Vite записывается в `.local/up-state.json` сразу после `spawn`, до ожидания
  готовности: `kill -9` в этом окне не оставляет процессы, которые следующий запуск принял бы
  за чужой стенд. Если запись невозможна (`ps` не отдал `lstart`), `up` гасит только что
  запущенный процесс и выходит с `1`, чтобы не оставить его без супервизора;
- после готовности падает только упавший сервис: супервизор ждёт backoff, поднимает его
  и пишет причину, хвост журнала и номер попытки в `.local/up.log`; соседние процессы
  сигналов не получают; после 5 неудач подряд `up` выходит с `1`;
- `kill -9` самого `up`: launchd поднимает новый; тот принимает **любой** живой хост,
  найденный `localInstance` (токен, `--server-data-dir`, порт и командная строка CLI),
  даже если запись в `up-state.json` не успела сохраниться, и пересоздаёт backend/Vite,
  подтверждённые записью (она создаётся сразу после `spawn`). Живой неучтённый
  backend/Vite — это ручной стенд: `up` ничего не сигналит и выходит с `0`;
- плановый `restart:services`/обновление: хосты перезапускаются штатной проверкой
  `activeSessions`; backend под супервизором не порождает второй процесс, а завершается
  кодом `75`, и `up` поднимает его заново. При активном ходе команда по-прежнему
  отклоняется.

Ручной `npm run up` остаётся fail-fast и не переживает внешнюю замену процессов: под ним
не запускайте `npm run restart:services`, `npm run update:agents` и кнопки
«Перезапустить службы»/«Обновления» — он заметит выход дочернего процесса и погасит
остальных. Для плановых перезапусков используйте `--supervised` (launchd).

Переход с уже работающего ручного стенда: `npm run autostart:install` создаст plist и job, но
новый `up` увидит живой неучтённый backend и по правилу чужого стенда выйдет с `0` — job
останется загруженным, но не работающим. Дальше остановите ручной `up` (Ctrl+C в его
терминале) и поднимите job: `launchctl kickstart gui/$(id -u)/com.agentcontrolcenter.up`.
Установка печатает ту же подсказку, когда видит живой стенд.

Диагностика:

| Симптом | Команда |
| --- | --- |
| Статус plist, job, стенда | `npm run autostart:status` |
| Job загружен, но не работает | `launchctl kickstart gui/$(id -u)/com.agentcontrolcenter.up` |
| Перезапустить супервизор принудительно | `launchctl kickstart -k …` — backend/Vite перезапускаются, активные ходы хостов переживают |
| Остановить автозапуск до следующего входа | `launchctl bootout gui/$(id -u)/com.agentcontrolcenter.up` (job выгружен, plist остаётся) |
| Остановить `up`, оставив job загруженным | `launchctl kill SIGTERM gui/$(id -u)/com.agentcontrolcenter.up` |
| Причина падения/перезапуска | `tail -n 100 .local/up.log` |
| Проверить plist | `plutil -lint ~/Library/LaunchAgents/com.agentcontrolcenter.up.plist` |
| Убедиться, что keep-awake работает | `pmset -g assertions \| grep -i caffeinate` |
| Кто держит порт | `lsof -nP -iTCP:8090 -sTCP:LISTEN` |

После `launchctl kill SIGTERM` job остаётся загруженным, но не запускается до `kickstart`
или следующего входа — это осознанная остановка (`up` перехватывает сигнал и выходит с кодом
`0`, поэтому `KeepAlive` его не поднимает). `launchctl bootout` выгружает job: до следующего
входа автозапуска нет, а `npm run autostart:install` вернёт job сразу через `bootstrap`.
`kickstart -k` убивает сам `up`; backend, Vite и хосты запущены в отдельных группах и переживают
его. Новый супервизор пересоздаёт backend/Vite по записи в `up-state.json`, а живые хосты
принимает без сигналов: активные ходы хостов не прерываются, но backend недоступен на время
перезапуска. Плановые перезапуски — через `npm run restart:services`.

Ограничения: LaunchAgent стартует после входа в GUI-сессию (при FileVault — после
разблокировки и входа), поэтому «доступно после перезагрузки» требует автологина или
обычного входа; label фиксированный, два checkout'а будут конфликтовать; после
обновления Node через nvm переустановите plist (`status` предупредит); журнал не
ротируется; падение самого хоста теряет его активные ходы — супервизор поднимает хост,
но не восстанавливает незавершённый ход.

Ручной запуск в отдельных терминалах остаётся для отладки:

```bash
npm run host        # Agent Host VS Code на ws://127.0.0.1:8089, данные в .local/host-data
npm run host:wbllm # Agent Host на ws://127.0.0.1:8093 для WBLLM
npm run host:glm   # Agent Host на ws://127.0.0.1:8094 для GLM
npm run server      # backend на 127.0.0.1:8090, читает hosts.json
npm run web         # интерфейс на http://localhost:5173
```

`up` не переживает внешнюю замену процессов: под работающим `npm run up` не запускайте
`npm run restart:services`, `npm run update:agents` и кнопки «Перезапустить службы»/«Обновления»
в панели — он заметит выход дочернего процесса и погасит остальных. Остановите `up` и запустите
снова. В режиме `npm run up -- --supervised` (его использует launchd) внешние перезапуски
поддерживаются: живые хосты принимаются, backend перезапускается по коду `75`.

VS Code CLI выводит адрес хоста с токеном подключения. `npm run host -- --log` и
`npm run host:wbllm -- --log` и `npm run host:glm -- --log` добавляют вывод в `.local/host.log` и `.local/wbllm-host.log` и `.local/glm-host.log`
соответственно и выставляют права `600`. При перенаправлении вывода средствами shell
перед созданием нового файла задайте `umask 077` в том же терминале.

### Обновление агентов и AHP

Кнопка «Обновления» рядом с заголовком проверяет версии SDK, клиента AHP и локального
Agent Host. После подтверждения панель устанавливает обновления и перезапускает
затронутые службы. Для перезапуска хосты должны освободиться от активных задач.
Из панели управляются локальные хосты `local`, `wbllm` и `glm`, запущенные скриптами проекта через VS Code Stable.

`npm run update:agents` загружает стабильные версии Codex App Server и клиента AHP
из npm в `.local/agent-sdks`. Новая версия становится доступна после проверки.
После успешной установки **всех** компонентов команда вызывает `npm run restart:services`
и перезапускает все локальные хосты и backend. Если хотя бы один компонент не установлен,
службы не перезапускаются. Для запуска со штатными версиями VS Code задайте `AHP_USE_BUNDLED_SDK=1`.

`npm run restart:services` можно выполнить и отдельно после ручного обновления зависимостей.
Команда управляет только локальными хостами из `hosts.json` и backend; основной и резервный UI не перезапускает.
Она проверяет все хосты до первого сигнала процессам, блокируется при активных задачах,
запускает остановленные хосты и повторно проверяет активность перед остановкой запущенных.
Backend заменяется только после успешного подключения всех локальных хостов. При сбое проверьте
`.local/host.log` и `.local/wbllm-host.log` и `.local/glm-host.log`. Backend должен быть запущен заранее:
при его недоступности пакеты могут быть обновлены, но службы не перезапускаются.

Эта же команда проверяет совместимые обновления клиента `@microsoft/agent-host-protocol`.
Новая версия проходит проверку TypeScript и тесты AHP в отдельном каталоге до установки.
Backend использует обновлённую библиотеку при следующем запуске `npm run server`.
Сервер Agent Host обновляется через штатный механизм VS Code CLI.

## Здоровье и журналы

Кнопка «Диагностика» в шапке сайдбара (адрес `#health`) открывает страницу, где собрана
диагностика в одном месте:

- backend: версия панели и клиента AHP, время запуска, включён ли доступ с телефона,
  состояние связи браузера с backend;
- каждый хост: живой статус (`connected` / `connecting` / `reconnecting` / `failed` /
  `disconnected`), причина, версия Agent Host и AHP, версии SDK агентов, время последнего
  успешного подключения и последнего события, число активных сессий;
- последние ошибки подключения — до пяти записей с момента запуска backend; повтор той же
  причины не вытесняет остальные, а увеличивает счётчик `×N`;
- хвост журнала локального хоста с автообновлением раз в 5 секунд и ручной кнопкой;
- кнопки «Подключить снова» и «Перезапустить службы» — существующие операции `reconnectHost`
  и `restartServices`. Ошибки показываются рядом с карточкой, страница при этом остаётся доступной.

Живой статус и причина приходят тем же push `overview`, что и в «Хосты и агенты». Версии,
история ошибок и журнал — снимок по запросу: при открытии страницы, по кнопке «Обновить данные»,
после успешной операции и после переподключения к backend.

Журнал читает backend (операция `readLog`), браузер не получает доступ к файлам напрямую:

- доступны только три фиксированных файла — `.local/host.log` и `.local/wbllm-host.log` и `.local/glm-host.log`
  (`npm run host -- --log` и `npm run host:wbllm -- --log` и `npm run host:glm -- --log`); каталог `.local` и произвольные
  файлы не отдаются, других путей у операции нет;
- хвост ограничен 64 КиБ и 300 последними строками, каждая строка — не длиннее 4000 символов;
- отсутствие файла — понятное состояние с подсказкой о команде запуска (кнопка «Перезапустить
  службы» тоже запускает хосты с `--log`), а не ошибка транспорта;
- символические ссылки, каталоги и не-regular файлы отклоняются без чтения содержимого;
- перед показом текст очищается от типовых секретов: query-параметры `tkn`/`token`/`api_key`/…,
  `Bearer`, переменные вида `*_KEY`, `*_TOKEN`, `PASSWORD`, отдельные 64-символьные hex-токены.
  Это best-effort защита в глубину: журнал может содержать локальные пути и текст сессий,
  поэтому доступ к нему остаётся в той же доверенной модели, что и управление агентами.

Удалённые хосты показывают диагностику без журнала — их файлы живут на другой машине.
Журналов нет и на не-macOS: `localHosts()` возвращает пустой список, потому что локальные хосты
управляются скриптами проекта через VS Code Stable.

Backend не пишет файл журнала: его вывод идёт в stdout терминала, где запущен `npm run server`.
Если раньше перенаправляли вывод в `.local/backend.log` вручную, панель этот файл не читает.

История ошибок живёт в памяти backend и сбрасывается при его перезапуске. С телефона страница
доступна по тому же Tailscale-адресу и тому же `/ws`: отдельных HTTP-маршрутов и новой
авторизации нет.

## Доступ с телефона

На Mac и телефоне подключите одну учётную запись Tailscale. Создайте
`.local/phone-access.json` с HTTPS-адресом этого Mac и логином Tailscale:

```json
{
  "origin": "https://my-mac.my-network.ts.net",
  "login": "me@example.com"
}
```

Выполните `npm run build`, затем запустите или перезапустите `npm run server`.
При наличии этого файла backend отдаёт собранную панель на `127.0.0.1:8092` и разрешает
запросы страницы и WebSocket только для указанного логина через Tailscale Serve.
Опубликуйте её внутри своей сети командой `tailscale serve --bg --https=443 8092`.
При первом запуске Tailscale может попросить включить HTTPS в браузере.
Откройте напечатанный HTTPS-адрес на телефоне. [Документация Tailscale Serve](https://tailscale.com/docs/features/tailscale-serve).

Для доступа с телефона должны работать backend и Agent Host. Во время работы Mac должен
оставаться включённым и бодрствовать. Путь к рабочей папке указывайте на Mac.
После обновления интерфейса пересоберите панель и перезапустите backend.

### Push-уведомления

Собранная панель — устанавливаемая PWA: backend отдаёт `/sw.js`, `/manifest.webmanifest` и
`/icons/*.png`, сохраняя проверку Tailscale. На iPhone откройте HTTPS-адрес в Safari,
нажмите «Поделиться» → «На экран Домой» и запустите панель с иконки: push на iOS работает
только для PWA с домашнего экрана (iOS 16.4+), во вкладке Safari — нет. На Android и в
Chromium достаточно открыть панель по HTTPS.

В панели нажмите «Уведомления» → «Включить» и разрешите уведомления. Кнопка
«Проверить уведомление» отправляет тестовый push на это устройство. Там же уведомления
выключаются: локальная подписка снимается, запись на backend удаляется.

Что приходит:

- сессия перешла в ожидание подтверждения инструмента или ответа агента;
- ход завершился (`InProgress → Idle`);
- ход завершился ошибкой.

Уведомление приходит только на переход состояния: повторная сводка или повторный action
дублей не даёт. Устройство, на котором эта сессия уже открыта и вкладка видима, push не
получает — остальные устройства получают. После перезапуска backend уже существующие
состояния считаются baseline и не уведомляют. Переходы, которые целиком укладываются в
30-мс объединение сводок, могут быть не замечены. Нажатие на уведомление открывает нужную
сессию и чат через hash-адрес.

Непрочитанные в панели не зависят от push: badge считается по сводкам, даже если
уведомления выключены или подписки нет. И наоборот, `InputNeeded` даёт push, но не даёт
непрочитанный ход — семантика описана в разделе «Закрепление и непрочитанные».

Backend хранит VAPID-ключи и подписки вне Git, в `.local`:

- `.local/push-vapid.json` — `subject`, `publicKey`, `privateKey`; файл и каталог создаются
  с правами 0600/0700. `subject` по умолчанию — `https://github.com/ShabanovBoris/agent-control-center`.
  Если push-сервис отклоняет subject, отредактируйте поле `subject` и перезапустите backend;
  ключи и подписки при этом не меняются.
- `.local/push-subscriptions.json` — endpoint, ключи, origin и время создания подписки.
- `.local/session-user-state.json` — закрепления (общие) и счётчики непрочитанных по origin;
  права 0600, временный файл и `rename`. Файл можно удалить при остановленном backend: pin и
  badge сбросятся, сессии на хосте не пострадают.

Приватный ключ и endpoint не передаются в браузер и не пишутся в логи. При смене VAPID-ключей
выключите и включите уведомления на каждом устройстве. Мёртвые подписки (404/410) backend
удаляет сам; при 401/403 подписка сохраняется, потому что причина может быть временной.
Нужны работающий backend, бодрствующий Mac и доступность push-сервисов Google/Mozilla/Apple;
offline-режима у PWA нет. Автозапуск backend и keep-awake — отдельные задачи.

## Первая настройка агентов

Чтобы подготовить SDK перед первым запуском, выполните `npm run update:agents`. В блоке
«Хосты и агенты» также доступна кнопка «Скачать SDK» для установки с CDN VS Code.
Основной хост «ChatGPT · Codex» использует вход через ChatGPT (`codex login`) и штатную
конфигурацию. `~/.codex/config.toml` скриптом запуска не меняется.
Для WBLLM и GLM заполните ключи по образцу `model-provider.env.example` и установите файлу
`.local/model-provider.env` права 600. Ключи не передаются в браузер и не хранятся в Git.

Codex показывает модели только после первой созданной сессии — до этого их список пуст.
Для основного хоста проверьте вход ChatGPT на машине хоста. Наличие модели в каталоге не гарантирует
её текущую доступность для генерации.

Рядом с полем сообщения видны модель и уровень reasoning. Панель передаёт уровень по умолчанию
из схемы выбранной модели вместе с сообщением (`message.model.config.thinkingLevel`), если хост
разрешает его менять. Конкретная модель запоминается в браузере для новых сессий этого хоста и
агента. В открытом чате восстанавливается его собственный выбор из черновика или истории.

В форме сообщения рядом с выбором модели доступны режимы, которые объявил хост. У Claude режим управляет подтверждениями
инструментов. У Codex режим работы и разрешения выбираются отдельно.
Изменение применяется после подтверждения хостом.

## WBLLM и GLM через Codex

Два отдельных хоста запускаются через `npm run up` или вручную:

```bash
npm run host:wbllm  # ws://127.0.0.1:8093
npm run host:glm    # ws://127.0.0.1:8094
```

| Хост | Responses API endpoint | Ключ |
| --- | --- | --- |
| WBLLM · Codex | `https://llm.wb.ru/api/v1` | `WBLLM_API_KEY` |
| GLM · Codex | `https://api.z.ai/api/v1` | `GLM_API_KEY` |

Ключи читаются из окружения или `.local/model-provider.env` (для launchd используйте файл).
Каждый хост получает каталог через `GET /models` своего endpoint и выбирает первую модель по умолчанию.
Наличие модели в каталоге не гарантирует поддержку Responses API и инструментов Codex.

Для каждого хоста создаются отдельные каталог моделей, данные, хранилище Codex и токен
в `.local/` с префиксом `wbllm-` или `glm-`. Основной хост продолжает использовать
Codex с входом ChatGPT. Дополнительные хосты переиспользуют Codex SDK основного хоста.

При переходе с отдельного хоста CheapVibeCode остановите прежний стенд штатным способом
и запустите новый после заполнения ключей. Данные прежнего хоста остаются в `.local/gemini-*`.

## Токены и архив

Под формой сообщения показаны сумма токенов, вход, выход и чтение кэша.
Учитываются все чаты сессии и текущий ход. Панель загружает старые страницы истории;
при ошибке показывает причину и кнопку повтора. Используются снимки usage хоста,
а не сумма входящих уведомлений: переподключение не удваивает расход.
Для Codex берутся суммы всех обращений к модели внутри хода, если хост их публикует.
Чтение кэша включено во вход и не прибавляется повторно к общей сумме.

Заполненность контекста относится к открытому чату. Для Codex и Gemini панель делит сумму
входных и выходных токенов последнего запроса на размер окна, переданный хостом. При отсутствии
данных хоста, в том числе у Claude, панель показывает «нет данных».

Если usage не передан или история неполная, это отмечено явно. Хост VS Code для Claude
не публикует токены записи кэша: показана нижняя граница по доступным данным, а не точный
биллинг провайдера. Счётчик показывает токены, не денежную стоимость.

Расход разложен по дням в часовом поясе браузера, по моделям и по чатам сессии. День берётся
из `startedAt` хода; ходы без даты попадают в «Без даты». Если история ещё грузится страницами
или хост не передал usage, суммы помечаются `≥` и подписаны как нижняя граница. Служебные
(hidden) чаты входят в расход сессии, хотя поиск их не индексирует.

Порог бюджета задаётся в токенах для открытой сессии и хранится в `localStorage` этого браузера
(`acc.tokenBudget.v1`) — без токенов доступа и других секретов. Панель сравнивает порог с общей
суммой и один раз уведомляет при переходе снизу вверх; повторные рендеры и StrictMode уведомление
не повторяют. Первое наблюдение выше порога после загрузки страницы тихое. Push и `Notification`
в проекте отсутствуют, поэтому уведомление показывается только в панели.

Кнопка «Отчёт по всем сессиям» строит отчёт на том же backend-слое истории, что и поиск:
кандидаты, страницы `fetchTurns`, семафоры, бюджеты, кэш и отмена. Отчёт по определению частичный:
он пишет, сколько чатов проверено, почему остановился и какие хосты ответили ошибкой. В отчёт
входят и служебные чаты. Денег, прайса, биллинга, прогнозов и экспорта в бухгалтерию нет — только
токены.

Кнопка «В архив» меняет состояние сессии на хосте через `session/isArchivedChanged`.
Архивные сессии доступны во вкладке «Архив»; «Восстановить» возвращает возможность
продолжить разговор. Это состояние общее для клиентов, а не локальное скрытие строки.

При удалении через другой AHP-клиент панель закрывает устаревшие подписки и показывает
«Сессия недоступна». Открытие уже удалённого адреса также заканчивается этим сообщением,
если хост отвечает `SessionNotFound` или `NotFound`.
Для не начатых черновиков VS Code может не прислать уведомление: выбранная сессия
дополнительно перепроверяется при возвращении фокуса в браузер и кнопкой «Обновить».

## Поиск и палитра команд

`Cmd+K` на macOS и `Ctrl+K` на Windows/Linux открывают палитру; на телефоне и для мыши
в сайдбаре есть кнопка «Поиск». Повторное нажатие закрывает палитру, `Escape` — тоже.

- Пока вы печатаете, сразу ищутся название сессии, провайдер (id и display name), хост,
  рабочая папка и названия чатов — только по `overview`, без загрузки истории.
- Совпадения по сообщениям и ответам из уже открытой (загруженной) истории показываются
  сразу. Через паузу ~300 мс backend догружает историю неоткрытых сессий: `watch`,
  страницы `fetchTurns` по курсору, затем `unwatch`. Параллелизм ограничен, поиск
  отменяется при смене запроса и закрытии палитры.
- Поиск по истории **по определению частичный**: ограничены число чатов, страниц на чат,
  одновременных запросов, время и количество совпадений. Палитра пишет, сколько чатов
  проверено, почему поиск остановился и какие хосты ответили ошибкой; при неполноте она
  не пишет «ничего не найдено». Ошибки хостов остаются видимыми в раскрывающемся списке.
- Выбор результата открывает сессию и чат. Для хода лента сама догружает страницы,
  прокручивается к нему и обводит его. Адрес `#host|session|chat|turn` переживает
  перезагрузку; старые ссылки `#host|session` и `#host|session|chat` работают как раньше.
- Не ищутся вложения, изображения, бинарники, вывод терминала и файлы на диске.
- Закрепление сессий и порядок «Недавних» описаны в разделе «Закрепление и непрочитанные»:
  pin меняет только порядок, состав результатов поиска прежний.

## Закрепление и непрочитанные

Строка сессии закрепляется кнопкой ★ и показывает badge непрочитанных ходов. Это состояние
панели, а не AHP-хоста: хост о нём не знает, контракт AHP не расширяется, других AHP-клиентов
оно не касается.

- **Закрепление общее для всех устройств.** Backend хранит его рядом с push-состоянием, оно
  переживает перезапуск. Закреплённые сессии идут первыми в любом фильтре и в архиве; внутри
  группы порядок прежний — по `modifiedAt` по убыванию. Отдельной вкладки, фильтра «Только
  закреплённые» и ограничения выдачи нет: pin сортирует, но не фильтрует.
- **Непрочитанные считаются для конкретного устройства (origin), а не глобально.** Счётчик
  увеличивается, когда ход завершился (`InProgress → Idle`, включая `InputNeeded → Idle`) или
  появилась новая ошибка, а сессия на этом устройстве не видима. `InputNeeded` сам по себе
  (агент ждёт подтверждения или ответа) непрочитанным не считается: об этом сообщают статус
  и push. Два устройства за одним origin (например, один Tailscale-адрес) делят счётчик;
  `localhost` и `127.0.0.1` — разные origin.
- **Сброс — когда сессия действительно видима.** Одновременно нужны: выбранная сессия,
  показанный detail (не форма новой сессии, не диагностика и не список на телефоне) и
  `document.visibilityState === 'visible'`. Открытие сессии или чата, deep link
  `#host|session[|chat[|turn]]`, клик по push и возврат в видимую вкладку сбрасывают счётчик
  этого origin. Скролл, фокус окна ОС и появление последнего хода на экране отдельно не
  отслеживаются: открытая сессия считается прочитанной целиком, а ответ пользователя — не
  отдельный триггер.
- **Архив.** Архивные сессии накапливают непрочитанные и показывают badge в фильтре «Архив»;
  в остальных фильтрах они скрыты, счётчики фильтров unread не учитывают.
- **Мобильный список.** На телефоне badge виден в списке, даже если сессия остаётся выбранной:
  скрытие badge привязано к показанному detail, а не к подсветке строки.

Backend хранит состояние в `.local/session-user-state.json` (`ACC_STATE_DIR`, права 0600,
атомарная запись через временный файл и `rename`):

- `pinned` — глобальный список `hostId + sessionUri`;
- `unread` — счётчики по origin; запись существует только при положительном счётчике и
  удаляется после сброса (нулевых `count` в файле и в сообщении backend нет);
- `origins` — известные устройства, чтобы считать непрочитанные и для закрытой вкладки.

При удалении сессии на хосте backend вычищает её pin, счётчики и снимок. Битый файл не
перезаписывается: pin и непрочитанные отключаются целиком, остальная панель работает; чтобы
начать заново, остановите backend и удалите файл. Ошибка записи не останавливает детектор:
состояние живёт в памяти и сохраняется следующей успешной записью, но до неё не переживёт
рестарт. Счётчик приблизительный: несколько ходов внутри 30-мс объединения сводок или во время
рестарта backend могут дать +1 вместо N или ничего, а новый origin начинает считать с момента
первого подключения — прошлые ходы ему не восстанавливаются. Pin и непрочитанные — свойство
этой панели, а не AHP: другие клиенты и сам хост их не видят.

## Выбор рабочей папки

В форме новой сессии кнопка «Выбрать в Finder…» открывает системный диалог выбора папки
на Mac с backend. Выбранный абсолютный путь подставляется в поле; отмена оставляет прежний путь.
Ручной ввод доступен для всех хостов.

Рядом есть «Дерево папок» — inline-браузер каталогов, пригодный с телефона и для удалённых
хостов. Оно показывает прямых детей каталога, позволяет перейти внутрь и вернуться наверх,
а «Выбрать эту папку» подставляет текущий путь в поле. Содержимое файлов не читается: файлы
видны, но не открываются. Основной источник — AHP `resourceList`; если хост отвечает
«метод не поддерживается» и это локальный хост проекта (тот, который панель запускает сама),
дерево строится по backend-листингу (`readdir`) с теми же именами и типами. Удалённому хосту
без `resourceList` дерево покажет текст об ошибке и предложит ввести путь вручную. На телефоне
и тач-экранах кнопка Finder скрыта: она открывает диалог на Mac, а не на устройстве.

«Недавние папки» хранит восемь последних директорий после успешного создания сессии.
История сохраняется в этом браузере, отдельно для каждого хоста; повторный выбор переносит
папку наверх списка. Ошибка сохранения истории не отменяет уже созданную сессию.

### Ветка и worktree

Под полем папки форма показывает текущую ветку: «Ветка: <имя>» или «Ветка: неизвестна».
Источник — только AHP-хост. Панель вызывает `resolveSessionConfig` для выбранной папки, а затем
повторяет запрос с принудительным `target: workspace` (`isolation: folder` у VS Code-хоста):
в этом режиме хост отдаёт текущую ветку. Если папка не git, HEAD в detached-состоянии или хост не публикует
поле ветки, форма пишет «неизвестна» и не подставляет default branch. Панель не читает git,
не переключает ветки и не создаёт worktree.

Если схема хоста предлагает `target: workspace|worktree` (или `isolation: folder|worktree`),
появляется выбор «Куда создать сессию». Для worktree показывается «Базовая ветка»: статический
`enum` рисуется списком, `enumDynamic` — полем с подсказками из `sessionConfigCompletions`
(запрос по мере ввода, с задержкой). Все значения приходят из ответов хоста; выбранный `config`
уходит в `createSession` вместе с рабочей папкой.

Выбор пользователя не ждёт повторного ответа хоста: «Создать», нажатая сразу после смены target,
отправляет выбранный `target` и введённую ветку, а блок не исчезает на время запроса. Defaults
(`values`) хоста применяются только к тому target, для которого они получены: до ответа на новый
запрос панель не подставляет ветку из прежнего режима.

Хост без `resolveSessionConfig` отвечает `-32601`: блок выбора скрыт, ошибка не показывается,
сессия создаётся как раньше. Отсутствие `sessionConfigCompletions` (тоже `-32601`) блок не скрывает:
подсказки остаются из схемы (обычно одно значение default), ошибка списка видна, ветку можно
ввести вручную. Любая другая ошибка хоста видна текстом в форме, но не блокирует создание.
Незагруженные динамические подсказки оставляют уже выбранную ветку и тоже не блокируют создание.

## Терминал

Кнопка «Терминал» в шапке открывает страницу `#terminal`: выбираете хост и папку (поле, дерево
папок через `listDirectory` и недавние), нажимаете «Открыть терминал» и получаете настоящий shell
в контексте проекта — в том числе с телефона по Tailscale.

- **Поток вывода** не идёт через состояние React. Backend копит `terminal/data` и отдаёт их
  кадрами `terminalData` не чаще ~30 раз в секунду и не больше 128 КБ на кадр, байты не теряются;
  остальные действия канала (`exited`, `resized`, `cleared`, `claimed`, `cwdChanged`) обновляют
  состояние как обычно. Браузер пишет кадры прямо в xterm. Кадры, пришедшие до монтирования
  эмулятора, ждут в буфере до 256 КиБ: при экстремальной скорости начало этого окна может
  потеряться, дальше буфер не растёт.
- **Эмулятор ленивый.** `@xterm/xterm` и `@xterm/addon-fit` грузятся отдельным чанком только на
  этой странице, поэтому основной бандл панели на них не растёт. Скроллбек ограничен 5000 строк,
  ресайз уходит на хост с debounce ~150 мс, фокус ставится в терминал при открытии.
- **Статус** показывает фактический `cwd` из состояния канала (хост мог не принять запрошенный
  путь), lifecycle `running`/`exited` с кодом выхода и фактические `cols×rows`.
- **PTY живёт до «Закрыть терминал»**: уход со страницы и F5 его не убивают, URI хранится
  в `localStorage` по паре хост+папка, а последняя открытая пара запоминается отдельно — поэтому
  после перезагрузки страница возвращается к тому же shell, даже если папка не совпадает с папкой
  по умолчанию. Если хост отвечает `NotFound` (терминал закрыт, backend
  или хост перезапускались), страница создаёт новый. Claim остаётся за backend-клиентом из
  `.local/client-ids.json`, поэтому после рестарта backend тот же shell остаётся нашим.
- **Лимиты.** Своих одновременных терминалов не больше восьми: новый вытесняет старейший без
  наблюдателей, а если все восемь открыты — панель просит закрыть один. Раз в минуту автоочистка
  закрывает свои терминалы без наблюдателей дольше `ACC_TERMINAL_IDLE_MS` (по умолчанию 30 минут).
  Терминалы агентов (`claim.kind === 'session'`) не трогаются никогда.

### Безопасность терминала

Доступ к терминалу — тот же, что к чату: страница по Tailscale проходит через
`tailscale-user-login` и сверку Origin, отдельного барьера нет. Подтверждения команд нет:
shell в контексте проекта запускается без approvals — это решение владельца и осознанная
граница доверия, а не забытая настройка. Один терминал на страницу, шаринга между устройствами
нет: `claim` не замок, и второй клиент может писать в чужой PTY.

## Конфигурация

`hosts.json`:

- `listen.host` — адрес входящего backend listener. Разрешены только `127.0.0.1` и `::1`;
  точное значение `localhost` при загрузке заменяется на `127.0.0.1`. Другие адреса и имена,
  включая `0.0.0.0`, отклоняются до подключения к AHP-хостам и открытия сокетов: backend
  исполняет команды агентов от вашего имени, а проверка `Origin`/`Host` не аутентифицирует
  произвольного сетевого клиента. Доступ с телефона настраивается отдельно через Tailscale Serve.
- `listen.port` — порт backend (по умолчанию `8090`).
- `agents` — какие агенты показывать (по `provider`); без списка показываются все.
- `hosts` — AHP-хосты: `id`, `label`, `url` и `tokenFile` с токеном подключения. Ограничение
  `listen.host` не ограничивает исходящие подключения backend к удалённым `hosts[].url`.
- `hosts[].defaultModels` — модели панели по умолчанию для агентов, которые не объявляют их
  по AHP. Ключ — id агента, значение — id модели из каталога этого хоста.
- `hosts[].localFilesystem: true` — файловая система хоста совпадает с Mac, на котором работает
  backend. Только для таких хостов на macOS доступен Finder. Для SSH-пробросов к удалённым
  машинам этот флаг не устанавливайте: локальная папка не является папкой удалённого хоста.
  Backend-листинг дерева устроен строже: он доступен только хостам из `localHosts` (macOS,
  id `local`/`wbllm`/`glm`, ожидаемый `tokenFile` и `127.0.0.1`), а не всем `localFilesystem`;
  allowlist вычисляется из этого же `hosts.json` при старте backend.
- `debugPort` — порт резервной панели, по умолчанию `5174`.

Основная и резервная панели читают один и тот же `hosts.json`. Резервная панель запускается
командой `npm start --prefix debug-ui` на `http://127.0.0.1:5174` и подключается к тем же
двум AHP-хостам напрямую. После изменения `hosts.json` её нужно перезапустить отдельно.
Токены читают backend и сервер резервной панели; в браузер они не попадают.

Для разработки есть отдельные mock-only конфиги `hosts.dev.json` и `hosts.e2e.json`: в каждом
только хост `mock` на `ws://127.0.0.1:8189`, `listen.port` 8095 и `agents: ["mock"]`, без
`tokenFile` и `localFilesystem`. Их читают `npm run server:dev` и `npm run server:e2e`;
production `hosts.json` они не меняют.

Удалённый хост проще всего подключить через SSH-проброс порта и добавить в `hosts` как ещё одну запись:

```bash
ssh -N -L 8189:127.0.0.1:8089 user@remote
```

## Разработка

Учебный контур без VS Code CLI, токенов и `.local` — три процесса в отдельных терминалах:

```bash
npm run mock-host     # AHP-хост на ws://127.0.0.1:8189
npm run server:dev    # backend на 127.0.0.1:8095, конфигурация hosts.dev.json
npm run web:dev       # панель на http://127.0.0.1:5173, прокси /ws на 8095
```

`hosts.dev.json` и `hosts.e2e.json` содержат только хост `mock`: без `tokenFile`, без `local` и
`wbllm`/`glm`, без файлов токенов локальных хостов. Production `hosts.json` и запущенные
реальные хосты они не меняют. `server:dev` и `server:e2e` выставляют `ACC_PHONE_ACCESS=0`, поэтому
не занимают порт 8092 и не читают `.local/phone-access.json`.

Mock-хост отвечает эхом с markdown-стримингом, на слово `tool` просит подтвердить `mock_shell`,
на слово `input` показывает карточку ввода, на слово `markdown` добавляет заголовок, список,
таблицу и длинный code block. После завершённого хода в панели доступен боковой чат
(`createChat`); история живёт в памяти, снимок чата отдаёт последние 6 ходов, а кнопка «Ранние
сообщения» грузит остальное через `fetchTurns`. После перезапуска mock-host история пропадает.

Порты переопределяются через env: `MOCK_HOST_PORT=8190 npm run mock-host` или
`npm run mock-host -- 8190` (аргумент важнее env); для backend — `ACC_PORT=8096` и
`ACC_MOCK_HOST_URL=ws://127.0.0.1:8190`; для панели — `ACC_BACKEND=127.0.0.1:8096 npm run web:dev`.
При смене порта mock задавайте пару `MOCK_HOST_PORT` + `ACC_MOCK_HOST_URL`, иначе backend продолжит
искать 8189. `npm run server:e2e` поднимает тот же backend на 8095 с `hosts.e2e.json`.
`ACC_STATE_DIR` задаёт каталог состояния backend (файл доступа с телефона, VAPID-ключи, подписки,
clientId, закрепления и непрочитанные); по умолчанию это `.local`, а E2E пишет в `test-results/state`.

Проверки:

```bash
npm run typecheck
npm test
npm test --prefix debug-ui
npm run test:e2e
```

`npx tsx scripts/probe.ts` проверяет AHP-хост напрямую с общим таймаутом 10 секунд.
`npx tsx scripts/backend-check.ts` проверяет backend. Таймаут подключения — 5 секунд,
время ожидания после подключения задаёт `CHECK_WAIT_MS` (по умолчанию 3000 мс).
По умолчанию доступны сводка, подписки и команды чтения. Для команд, меняющих состояние хоста,
передайте `--write` первым аргументом перед JSON-командами.

Диагностика и журнал — тоже read-only, `--write` им не нужен:

```bash
npx tsx scripts/backend-check.ts '{"op":"health"}' '{"op":"readLog","hostId":"local"}'
```

`health` возвращает снимок версий и истории ошибок, `readLog` — хвост журнала локального хоста;
неизвестный `hostId` отклоняется сообщением «Журнал доступен только для локальных хостов проекта».

### E2E-тесты

`npm run test:e2e` поднимает mock-контур и прогоняет панель в Chromium. Первый запуск сам ставит
браузер (`pretest:e2e`); на Linux без системных библиотек предварительно выполните
`npx playwright install --with-deps chromium`.

Что запускается: mock-хост на `ws://127.0.0.1:8190`, backend на `127.0.0.1:8096` с
`hosts.e2e.json` и Vite на `http://127.0.0.1:5175`. `reuseExistingServer: false` не даёт
подключиться к чужому серверу: production 8090, dev-контур 8095/8189, резервная панель 5174 и
`.local` не затрагиваются. Состояние backend (VAPID-ключи, clientId, закрепления и счётчики
непрочитанных) пишется в `test-results/state` через `ACC_STATE_DIR`; поэтому тесты, которые
закрепляют сессию, обязаны снимать pin за собой.

`e2e/directory-tree.spec.ts` проверяет дерево папок на ширине 390 px: детерминированный
`resourceList` mock-хоста, сортировку «каталоги раньше файлов», вход/вверх, выбор пути,
отсутствие горизонтального overflow и текстовую ошибку для несуществующего каталога.

Порты переопределяются через env:
`E2E_MOCK_PORT=8290 E2E_BACKEND_PORT=8097 E2E_WEB_PORT=5176 npm run test:e2e`.
Занятый порт даёт понятную ошибку с подсказкой; чужой процесс Playwright и fixture не убивают.

Один сценарий или группа:

```bash
npm run test:e2e -- e2e/copy-response.spec.ts
npm run test:e2e -- --grep "markdown"
npm run test:e2e -- --headed
npm run test:e2e -- --debug
```

Отчёт лежит в `playwright-report/index.html`; `npx playwright show-report` открывает его.
При падении Playwright сохраняет screenshot и trace в `test-results`, trace открывается командой
`npx playwright show-trace test-results/<каталог теста>/trace.zip`. Ретраев нет: нестабильный
сценарий падает на первом прогоне. Покрытие — Chromium, последовательный прогон, без визуального
диффа скриншотов и реальных моделей.

### CI

GitHub Actions workflow [`.github/workflows/ci.yml`](.github/workflows/ci.yml) запускается на каждый
pull request и на push в `main`. Job `verify` работает на Node.js 22 и выполняет:

```bash
npm ci
npm ci --prefix debug-ui
npm run typecheck
npm test
npm test --prefix debug-ui
npm run build
```

Job `e2e` идёт после `verify`, кэширует Chromium по ключу lockfile и выполняет
`npx playwright install --with-deps chromium` и `npm run test:e2e`. При падении он выгружает
`playwright-report/` и `test-results/` артефактом (без `test-results/state`).

Кэш npm учитывает оба lockfile. Секреты, `.local`, реальные AHP-хосты и VS Code CLI не нужны:
проверяются unit-тесты, production-сборка и E2E на mock-контуре. Деплой, публикация артефактов,
линтер и форматтер в workflow не входят.

`npm run build` предупреждает о чанке больше 500 kB; предупреждение не подавляется и сборку не валит.
Размер entry на 24 ноября 2026 в ветке AGENTHOS-16 — 542.24 kB (gzip 164.67 kB), на базе
`e74368d` до изменений было 537.82 kB (gzip 163.31 kB); подсветка кода вынесена в ленивый чанк
`highlight-*.js` — 70.99 kB (gzip 23.59 kB), который запрашивается один раз при первом блоке
с меткой `language-*` — в том числе для языка без зарегистрированной грамматики; в этом случае
блок остаётся обычным `<pre><code>`. После ребейза на `main` цифры нужно перемерить. Цифры
и ссылки на прогоны — в [memory-bank/AGENTHOS-16.md](memory-bank/AGENTHOS-16.md).

Check `verify` включён как required для pull request в `main`. Required status checks проверяются
только при merge PR; прямые push в `main` проходят мимо branch protection, потому что правила к
администраторам не применяются (`enforce_admins: false`) и отдельного требования «только через PR»
нет.

## Устройство

- `server/hub.ts` — соединения с хостами через `MultiHostClient` из SDK, перевод команд UI в AHP actions.
  Также ждёт снимки/страницы каналов, сериализует `fetchTurns` одного чата и отдаёт поиску
  узкий интерфейс `SearchEnvironment`.
- `server/mirror.ts` — зеркало состояния каналов; упорядочивает снимки и actions по `serverSeq`.
- `server/session-user-state.ts` — состояние панели вне AHP: глобальные закрепления, счётчики
  непрочитанных по origin, детектор завершения хода и новых ошибок, сериализованная запись и
  очистка по `sessionRemoved`. `server/session-snapshot.ts` — общий снимок сводки для push и
  непрочитанных, `server/state-file.ts` — атомарная запись 0600, `server/origin.ts` — разбор origin.
- `server/presence.ts` — `visibleOrigins`/`visibleSessions`: одна трактовка «сессия видима на
  устройстве» для подавления push и сброса непрочитанных.
- `src/session-list.ts` — порядок списка (закреплённые первыми) и счётчики badge;
  `src/panel-presence.ts` — единый предикат «detail реально показан» для presence и badge.
- `src/session-config.ts` — schema-driven разбор конфигурации новой сессии: `target`/`isolation`,
  `baseBranch`/`branch`, probe текущей ветки, payload для `createSession` и деградация по `-32601`.
  React-форма только рендерит разобранную схему и значения хоста.
- `server/search.ts`, `server/search-cache.ts` — backend-поиск по истории: кандидаты, бюджеты,
  семафоры, страницы по курсору, неполнота и ограниченный in-memory кэш извлечённого корпуса.
  `HistorySearch.usageReport` переиспользует этот слой для отчёта по расходу, включая hidden-чаты;
  общий `loadCandidate` не создаёт второй механизм загрузки.
- `shared/usage.ts` — единый расчёт токенов: строки по моделям и датам, суммы, `partial`/`hasMoreTurns`,
  поправка Claude и выбор часового пояса. Используется панелью, backend-отчётом и тестами parity.
- `src/usage-budget.ts` — порог в `localStorage` и `BudgetLatch` вне React: одно уведомление на переход.
- `src/UsageTables.tsx`, `src/usage-format.ts`, `src/UsageReportDialog.tsx` — таблицы «день × модель»,
  форматирование нижней границы и диалог отчёта с загрузкой, отменой и ошибками.
- `shared/search.ts` — нормализация (`ё/е`, регистр, карта индексов), токены, веса полей,
  ранжирование, сниппеты и извлечение текста хода. Используется браузером и backend.
- `src/search.ts` — overview-поиск, локальный корпус загруженной истории, слияние с deep-результатами
  и текст статуса полноты; React и WebSocket сюда не входят, поэтому модуль тестируется в Node.
- `scripts/mock-host.ts` — учебный AHP-хост для dev/e2e: эхо, подтверждение инструмента, ввод,
  markdown-отчёт с таблицей, боковой чат, постраничная история, а также `resolveSessionConfig`
  и `sessionConfigCompletions` с детерминированным набором веток; запускается через `npm run mock-host`.
- `server/health.ts` — снимок здоровья: backend, хосты, версии SDK, история ошибок по запросу `health`.
- `server/logs.ts` — allowlist журналов локальных хостов и хвост с лимитами; `server/redact.ts` — редакция секретов.
- `server/host-issues.ts` — ограниченная история ошибок подключения; `server/host-build.ts` — общий
  парсер `_meta.hostBuild`.
- `shared/` — контракт backend ↔ браузер и общие редьюсеры: браузер получает снимок и actions
  и применяет те же редьюсеры SDK, что и backend.
- `src/` — интерфейс на React; `src/HealthView.tsx` — страница `#health`.
- `scripts/claude-provider.mjs` — настройки API для `query`, `startup` и `prewarm` Claude SDK;
  остальные экспорты, включая историю сессий, делегируются установленному SDK без изменения.

## Ограничения

- Статус SDK агентов и запрос на его скачивание идут через служебные ключи VS Code в root config,
  а не через стандартный AHP; на других хостах этого блока не будет.
- Copilot в панели скрыт списком `agents`. Сам хост VS Code регистрирует его всегда, отключить
  его на хосте нельзя; для работы ему понадобился бы GitHub-токен от клиента, чего панель не умеет.
- Просмотр файлов ограничен правками конкретного хода: `FileEditDisplay` показывает данные
  `FileEdit` из результатов успешных вызовов инструментов, а для хода из истории без прямых данных
  может запросить `turn`-changeset при распознанном успешном вызове инструмента правки, если хост
  публикует шаблон URI хода. Текстовый diff доступен, если хост сохранил читаемые версии файлов.
  Это не файловый браузер и не просмотр произвольных изменений на диске.
- Переход из карточки подагента открывает его чат, только если чат опубликован в каталоге сессии
  и не hidden. Если хост не опубликовал worker-чат, карточка показывает поля из ответа и сообщает,
  что чат недоступен.
- Терминал — только вкладка `#terminal`: нет табов и нескольких PTY в интерфейсе, нет шаринга
  одного shell между устройствами и нет read-only просмотра терминалов агентов. Переименования
  нет: `terminal/titleChanged` хост принимает, но заголовок не меняет. Снимок канала хост обрезает
  (~82 КБ), поэтому после переподключения старый вывод неполный — принимается. Кириллица в поле
  `commandLine` command-парта приходит искажённой на стороне хоста; вывод при этом верный, панель
  это не «чинит».
- Ветка и worktree в форме новой сессии зависят от возможностей хоста: текущую ветку панель
  узнаёт только через probe `resolveSessionConfig` в режиме текущей папки. Хост без метода,
  не-git папка и detached HEAD дают «ветка неизвестна», а список веток ограничен ответами хоста.
  Панель не делает checkout, не создаёт ветки/worktree и не читает git в обход AHP.
- Диагностика показывает историю ошибок подключения только с момента запуска backend: она живёт
  в памяти, ограничена пятью записями на хост, а повтор одной причины считается счётчиком. Журналы
  доступны только у локальных хостов проекта и только три фиксированных файла `.local/*.log`;
  файла журнала backend нет — его вывод идёт в stdout.
- Редакция секретов в журнале и причинах — best-effort: неизвестные форматы токенов могут остаться,
  а локальные пути и текст сессий в журнале не скрываются. Доступ к странице остаётся в той же
  доверенной модели, что и управление агентами (loopback или Tailscale-логин).
- Нет выбора из нескольких рабочих папок и подтверждения результата инструмента.
- Дерево папок показывает только имена и типы прямых детей: содержимое файлов не читается,
  записи не меняются, поиска по файловой системе нет. Поддержка `resourceList` не кэшируется —
  каждый переход делает один вызов и при `-32601` уходит в backend-листинг. Симлинки в
  backend-листинге отображаются файлами (без `stat` и перехода по ссылке), а `..` в ручном пути
  разбирается лексически: для пути через симлинк он может означать не тот каталог. Если хост
  запрещает каталог, «Вверх» покажет ошибку; вернуться можно повторным открытием дерева
  (оно начнётся с поля) или ручным вводом. Доступ наследует доверенную модель панели
  (loopback или Tailscale-логин) и не расширяет права на файловую систему сверх листинга.
- Поиск по истории не индексирует вложения и бинарники и не читает файлы на диске. Кэш корпуса
  живёт только в памяти backend: после рестарта он пуст, TTL 10 минут, объём ограничен.
  Очень длинные ответы обрезаются лимитом текста на ход и помечаются причиной `text-budget`.
  Если хост не обновляет `modifiedAt`, кэш закрытого чата может быть свежим до TTL.
  Отмена поиска прекращает новые страницы, но уже отправленный запрос AHP отменить нельзя:
  SDK `request` не принимает `AbortSignal`.
- Поиск по истории ограничен бюджетом (40 чатов, 10 страниц на чат, 6 секунд): полный обход
  всех сессий не выполняется.
- Закрепление и непрочитанные живут только в этой панели и не синхронизируются с AHP-хостом или
  другими клиентами. Счётчик непрочитанных приблизительный: переходы внутри 30-мс объединения
  сводок, рестарт backend и временное исчезновение сессии из сводки могут дать +1 вместо N или
  ничего. Origin — не физическое устройство: вкладки одного origin делят счётчик, а `localhost`
  и `127.0.0.1` считаются разными устройствами. Если сессию удалили, пока backend не работал,
  `sessionRemoved` не придёт и запись останется в файле, но в UI её не видно; полная сверка с
  хостом при старте невозможна, потому что хост может быть ещё не подключён.
- Порог расхода глобальный для браузера, а не для каждой сессии. Latch не переживает перезагрузку:
  после reload первое наблюдение снова тихое. Дневного порога и фонового polling нет — отчёт
  строится по кнопке; при пересечении порога во время догрузки истории уведомление относится
  к уже накопленному расходу.
- Отчёт ограничен теми же бюджетами поиска и может быть заметно неполным: сессии и чаты за
  пределами 40 кандидатов в него не попадают, о чём сигнализирует глобальный `≥`. Кэш хранит
  usage вместе с текстом и не учитывает строки usage в лимите `maxChars`. Унаследованный префикс
  side chat по-прежнему может учитываться дважды — parity с `sessionTokenUsage` сохраняется.
- E2E на Playwright покрывают создание сессии, отправку сообщения, markdown-стриминг, tool call,
  копирование ответа, переподключение хоста, мобильную ленту, закрепление с перезагрузкой и badge
  непрочитанных на десктопе и в мобильном списке 390 px. Поиск, ранжирование, кэш и отмена
  остаются за unit-тестами; палитра и переход к ходу проверяются вручную.
- Пути рабочих папок — только POSIX.
- Смену модели в уже идущей сессии Claude хост не применяет: ход выполняет прежняя модель.
  На первом ходе новой сессии выбор работает; Codex меняет модель и посреди сессии.
  Под каждым завершённым ходом панель показывает модель, которая его выполнила;
  то же по всей сессии выводит `npx tsx scripts/turn-models.ts <hostId> <ahp-session:/…>`.
- Повторный ответ на одно подтверждение хост VS Code не отклоняет, а принимает; инструмент при этом
  выполняется один раз. Backend сам отсекает ответ на вызов, который уже не ждёт подтверждения.
- Markdown-части ответа агента рендерятся с GFM. У каждого блока кода есть кнопка «Скопировать
  код» (включая код с отступом), блоки с `language-*` подсвечиваются: `lowlight`/`highlight.js`
  грузятся отдельным чанком при первом таком блоке. Поддерживаются `typescript`/`ts`/`tsx`,
  `javascript`/`js`/`jsx`, `json`, `bash`/`sh`/`zsh`, `python`/`py`, `go`/`golang`, `rust`/`rs`,
  `sql`, `yaml`/`yml`, `diff`/`patch`, `html`/`xml`, `css`, `markdown`/`md`; неизвестный язык
  и код без метки остаются обычным `<pre><code>`, автоопределения языка нет. Ссылки `file:line`
  и `vscode://` не открываются: безопасного предсказуемого способа нет.
  Raw HTML показывается текстом. Внешние картинки не загружаются — вместо них ссылка с alt-текстом;
  как изображение отображается только `data:image/`. Одиночный перевод строки внутри абзаца — мягкий
  перенос GFM: он схлопывается в пробел, как в GitHub; новый абзац задаётся пустой строкой.
  Широкие GFM-таблицы прокручиваются внутри своего блока, не растягивая ленту.

## UI Компоненты

Интерфейс включает набор компонентов для работы с расширенными возможностями агентов:

### Основные компоненты
- **ConfigPanel** — выбор режима работы (default/acceptEdits/plan/auto)
- **ChatSourceMenu** — боковой чат от текущего или последнего завершённого хода и форк переписки до последнего завершённого хода
- **ReasoningBlock** — свёрнутый блок рассуждений агента (вместо старого встроенного)
- **ToolResultsDisplay** — отображает `Text` как текст, для `EmbeddedResource` показывает превью
  PNG/JPEG/GIF/WebP, а для остальных форматов — только MIME-тип. `Resource` показывает URI обычным
  текстом, не открывая и не скачивая ресурс. В SDK 1.1.0 в `ToolResultContent` нет отдельных типов
  `Image` и `File`; `FileEdit` обрабатывается отдельно от карточки результата компонентом
  `FileEditDisplay`. `Terminal` рендерится карточкой `TerminalOutput`, `Subagent` — `SubagentCard`;
  неизвестные варианты `ToolResultContent` пропускаются.

### Вспомогательные компоненты
- **MarkdownMessage** — markdown-части ответа агента: заголовки, списки, цитаты, inline- и fenced-код,
  GFM-таблицы и task-list. У блока кода доступная кнопка «Скопировать код»: копирует исходный текст,
  показывает toast «Код скопирован» и галочку на 2 секунды; при отказе clipboard — toast с причиной.
  Fenced-блоки с известным языком подсвечиваются лениво (`CodeBlock` + `src/highlight.ts`), набор
  языков и поведение неизвестных — в разделе ограничений. Raw HTML выводится текстом; ссылки
  безопасных схем открываются в новой вкладке. Внешние картинки не загружаются и показываются
  ссылкой, `data:image/` — изображением. Соседние markdown-части конкатенируются в один блок, как
  display text в SDK; карточка инструмента остаётся границей. «Скопировать ответ» отдаёт markdown
  последнего непустого блока: части склеены, хвостовые пробелы срезаны.
- **AttachmentUpload** — загрузка изображений через file input
- **MessageView** — отображение сообщений с вложениями
- **FileEditDisplay** — список правок конкретного хода по данным `FileEdit` из успешных вызовов
  инструментов или, для хода из истории без прямых данных, по `turn`-changeset при распознанном
  успешном вызове инструмента правки и опубликованном хостом шаблоне URI хода. Текстовый diff
  строится по сохранённым версиям от хоста; общего файлового браузера и просмотра произвольных
  изменений на диске нет.
- **TerminalOutput** — сохранённый результат терминальной команды: заголовок, `result.preview`,
  код выхода, пометки `truncated` и PTY; длинный вывод свёрнут. Это карточка результата вызова
  инструмента, а не живой shell: он открывается на отдельной странице `#terminal`
- **SubagentCard** — карточка подагента: `title`, `agentName`, `description` и переход в его чат,
  если чат опубликован в каталоге сессии и не hidden
- **CommandPalette** — палитра `Cmd/Ctrl+K`: combobox/listbox с клавиатурной навигацией,
  группы «Сессии и чаты»/«Сообщения», статус полноты, ошибки хостов и повтор поиска.
- **HighlightedText** — подсветка совпадений через `<mark>`; диапазоны приходят из `shared/search.ts`
  в координатах сниппета, HTML не используется.

### Основные операции API
- `createChat` — создание нового чата с поддержкой fork и side-chat
- `fetchTurns` — получение истории сообщений курсором
- `searchHistory` — backend-поиск по истории (частичный результат с `reasons` и `issues`)
- `cancelSearch` — отмена текущего поиска браузера по id вызова
- `usageReport` — отчёт по расходу токенов на слое истории поиска; `cancelUsage` — его отмена
- `readResource` — чтение ресурса с хоста
- `listDirectory` — имена и типы прямых детей каталога: `resourceList` хоста либо backend-листинг
  локального хоста; результат `{ path, source, entries }`, где `source` — `host` или `backend`
- `updateSessionConfig`/`updateChatConfig` — изменение конфигурации

### Особенности
- Вложения в сообщениях преобразуются в `Message.attachments`
- Поддержка видения моделей отражена в `ModelOverview.supportsVision`
- Возможности агента (`multipleChats`, fork/side-chat) через `AgentCapabilities`
- Иконка скрепки без текста для экономии места в композере
